UX Changes by Domain#

AI Copilot Layer (global chat dock, agent sidebar, coworker presence)#

New: components/ai-layer/{AILayer,AgentAvatar,AgentSidebar,AskPxeAiLauncher,ChatDock,ChatWindow,PeerAvatar,ProductRowAIMenu,useAIContextSync,useAgentSend,useCoworkers}, lib/{ai-agents,ai-chat-client,ai-chat-store,ai-screen-context,coworker-chat-store}, supabase/functions/pxe-ai-agent/index.ts. Wired into App.tsx/DashboardLayout.tsx/Header.tsx.

  • Layout: AgentSidebar is a persistent right-hand collapsible rail (xl+ breakpoint only) inside DashboardLayout, listing 9 AI agents plus human "coworkers" with unread badges. AILayer (mounted once, floating) renders a bottom-right "Ask PXE AI" launcher + a ChatDock of up to 4 open mini chat windows (320×420px, minimizable/closable, "+N More" overflow), each a drag-drop target for product/attribute chips.
  • 9 AI agents (ai-agents.ts): Content Copilot, GEO Assistant, Compliance Agent, Attribute Mapper, Review Insights, Competitor Watch, Launch Assistant, Workflow Builder, Executive Assistant — each with icon, suggested prompts, action chips (Generate/Preview/Apply Changes/Publish).
  • Screen-aware context (ai-screen-context.ts): pathname → screen label + 3 contextual suggested prompts (Product Detail, Product Catalog, Vendor/Intake, Assortment, Promotions, Reviews, Insights, Retailer Flow, Dashboard, default).
  • Interactions: click an agent to open/stream a chat; drag a product row or an attribute-gap chip into a chat window to auto-prompt; ProductRowAIMenu adds a per-row Sparkles dropdown with 6 canned AI actions; Header's notification bell now wires to real unread coworker DMs (was a hardcoded "2"); coworker chat persists via Zustand + localStorage with desktop-style notifications.
  • Data shape: Conversation{ kind:'agent'|'coworker', agentId?, peer?, messages, minimized, unread, busy }, AIContext{ currentProduct?, selectedProducts[], filters, retailers[], categoryContext?, screen?, screenFocus? }.
  • Backend: pxe-ai-agent — Deno edge function proxying to Lovable's AI gateway (google/gemini-3-flash-preview), streaming SSE, injecting agent system-brief + JSON catalog context. No Supabase tables — all state is client Zustand persisted to localStorage plus a stateless streaming proxy.

Product Detail — Lineage & Provenance#

New: components/product-detail/lineage/* (11 files), lib/product-lineage-store.ts. Wired into ProductDetailPage.tsx, ProductAssetsTab.tsx, ProductAttributesTab.tsx.

  • New "Linkage Summary" tab (ProductLineageTab) plus a 3-way layout toggle (A · Lineage Tab / B · Command Center / C · Provenance Rail, persisted via ?layout=).
  • 8 "retailer questions answered": origin, submitting vendor(s), merge history, onboarding date, attribute provenance, asset count, readiness score, open gaps.
  • LineageJourney: 8-stage flow/timeline (Vendor Submission → Product Intake → Ready To Onboard → Onboarding → Graph Processing/merge → SKU Created → Catalog → current state).
  • LifecycleStatusBar: 8-state stepper (Submitted…Published) with a compact clickable variant opening a full explainer dialog.
  • ContributingSourcesPanel + VendorSourceDialog: ranked vendor-contribution bars/table, drillable into per-attribute accepted-vs-superseded survivorship and submission-basis facts (channel, cadence, format, match key/confidence, trust score).
  • RetailReadinessPanel: 0–100 composite score (completeness 25% / quality 20% / assets 20% / relationships 10% / validation 15% / approval 10%) with radial gauge, per-metric bars, gaps list.
  • RelationshipNetwork: radial SVG diagram of Parent/Variant/Bundle/Cross Sell/Up Sell relationships, filterable by relation type.
  • DigitalAssetsPanel (now embedded in ProductAssetsTab, replacing the old grid/list browser): required-vs-supplied counts per asset category with grouped/grid views and approval status.
  • ProductAttributesTab now shows a Source/Vendor/Confidence column per attribute plus a source-system filter dropdown.
  • Data shape: ProductLineage{ merchandisingSku, internalSkuId, sourceProductIds[], submissionChannels[], vendors[], isMultiVendor, sources: ContributingSource[], journey: JourneyStage[], readiness{score,verdict,metrics[],gaps[]}, assetCategories[], relationships[] } — all deterministic mock data keyed by a hash of productId. No backend.

  • Backend: product-copilot — same Lovable AI gateway pattern as pxe-ai-agent, with chat and extract-with-vision-tool-call modes.

Implementation Notes#

API/schema changes implied for a real port (loveable uses Supabase + Deno edge functions directly; none of this maps to existing oRPC contracts):

  • Lineage/provenance data (ProductLineage, ContributingSource, journey stages, readiness metrics, asset categories, relationships) is 100% client-generated mock data in loveable — a real port needs new oRPC contracts/procedures (e.g. a productLineage/provenance domain in @repo/core-contracts) backed by whatever actual survivorship/golden-record and DAM services exist upstream, since none of this is queried from anywhere real today.
  • The two Supabase edge functions (pxe-ai-agent, product-copilot) are streaming LLM proxies with no auth/RBAC beyond a Supabase anon key — a pxc-retail equivalent needs a new oRPC streaming procedure (or dedicated SSE route) through the existing authed/errorRecordingMiddleware pipeline, preserving the "never leak upstream details" discipline this repo already enforces.
  • AssetIntelligencePanel's vision-extraction call (mode:'extract') implies a new BFF endpoint accepting an image reference and returning structured metadata — needs a new Zod schema/contract for ExtractedAssetMetadata.
  • Household Management (HOUSEHOLDS, LINKS, RECOMMENDATIONS) is entirely static array mock data with toast()-only actions — a real port needs full CRUD contracts for households, member links (confidence/status/reject-reason), and recommendation accept/reject, none of which exist today.
  • RetailerFlow page is pure static content/deep-links — no new contracts needed, just navigation config + i18n strings.

Design-system component mappings needed (loveable uses shadcn/ui primitives directly, not @syndigo/design-system):

  • Sheet, Popover, ScrollArea, Collapsible, ToggleGroup/ToggleGroupItem, Tooltip, Dialog, DropdownMenu, Slider, Switch, Progress — confirm each has a @syndigo/design-system/components/<name> equivalent (some already used in pxc-retail per $productId.tsx).
  • recharts (used raw in HouseholdManagementTab for pie/bar/line charts) has no confirmed analog in this codebase — check the dataviz skill/design-system charting story before porting.
  • OKLch semantic tokens (text-success, text-warning, bg-success, border-warning/30) likely map directly, but raw Tailwind palette classes (text-emerald-500, text-amber-500, text-rose-500, text-cyan-500, used in ai-agents.ts tone strings and RelationshipNetwork's RELATION_META) need remapping to theme semantic tokens.

pxc-retail convention deviations (expected — this is a Lovable prototype):

  • Routing: react-router-dom (useNavigate, useSearchParams, <Route>) vs. pxc-retail's TanStack Router file-based routes with Zod validateSearch and beforeLoad permission guards — none of the new loveable routes/tabs have any permission/module-access check.
  • State: ad hoc Zustand stores (ai-chat-store, coworker-chat-store) persisted straight to localStorage, vs. pxc-retail's React Query + oRPC pattern for anything server-backed.
  • Data fetching: raw fetch() to Supabase Edge Function URLs with manual SSE line-parsing (ai-chat-client.ts, ProductCopilotPanel.tsx), vs. pxc-retail's oRPC client/createTanstackQueryUtils.
  • i18n: every new string is hardcoded English JSX — no useTranslation/selector callbacks anywhere, which directly violates this repo's i18n mandate; a port needs a full locale pass across en/es/fr/de.
  • Auth/session: previewAuthStorage.ts is a Lovable-preview-specific postMessage broker for sharing Supabase auth across the Lovable iframe/editor — inapplicable outside the Lovable authoring environment; discard rather than adapt.
  • Forms: HouseholdManagementTab's New Household wizard manages its own step state and manual validation (detailsValid, canProceed) rather than TanStack Form / the isDefaultValue dirtiness convention this repo mandates.
