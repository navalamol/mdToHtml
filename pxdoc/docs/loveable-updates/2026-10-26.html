UX Changes by Domain#

Validation Framework (new)#

A self-contained, client-only rule engine under src/lib/validation/ plus four shared React components, wired into the vendor record editor and the new-vendor request flow. No Zod, no server — pure functions returning a RuleResult { id, severity, message, trigger, section, field } envelope.

  • Shared components: ValidationSummaryBanner (sticky role="alert" "N errors, M warnings" with buttons that scroll+focus the offending field via data-testid); FieldMessages (FieldError/FieldWarning/FieldHint + RequiredSrLabel + errorInputClass); AddressFields (validated Country→Street→City→State/ZIP block with normalize-on-blur, aria wiring, subdivision selects); ValidationDebugDrawer (dev-only ?debug=1 Sheet listing pass/fail for the full rule catalog).
  • Shared behaviors: canSave (errors block Save; warnings require acknowledgement), shouldShow (messages appear only after touch or a save attempt), normalizeText (trim + collapse whitespace), stable field-<section>-<name> / msg-<section>-<name> test-ids.
  • Validators: ABA checksum, IBAN mod-97, SWIFT/BIC, EIN prefix + placeholder detection, DUNS, GS1/GLN check digit, SCAC, postal, E.164 phone (libphonenumber-js), email, https URL, 4-digit year.
  • Per-section schemas: vendorProfile (VP-001..015), banking (BK-001..018 + TX tax + TT trade terms), businessRisk (BR-001..027 D&B identity/hierarchy/scores/ownership/diversity), addresses (AD-001..025 incl. PO-box ban, sanctioned-country block, GLN, cold-chain, FFR), contacts (CT-001..014), documents (DC-001..019 incl. COI/FDA/GFSI/W-9 metadata, DocuSign), customFields (GEN/CP — ESG, attestations, SCAC, GDSN), onboarding (OB-001..005 approve/reject gates + segregation-of-duties), newVendorRequest, and rules.ts (XS-001..010 cross-section integrity on save).
  • Mocks: mockServices.ts client-side stubs (explicitly server-side TODOs) for routing lookup, duplicate-vendor, sanctions, TIN match, DUNS, address verify, malware scan, carrier authority; audit.ts mock RBAC + activity log; config.ts D&B/insurance/sanctions/disposable-domain data.

Implementation Notes#

  • Architecture divergence (the recurring theme). Loveable persists runtime state client-side — Zustand stores (added-vendors-store + Supabase realtime, bank-change-store + localStorage) and per-user local/sessionStorage for list state — and ships one monolithic client-only RuleResult[] engine with English strings baked in. pxc-retail is contract-first: data flows through oRPC (orpc.vendorCentral.tenantVendor.*) with cursor pagination and @repo/core-contracts/schemas/vendor-schema; validation rules are pure functions in core-contracts/vendor-central/* returning { field, ruleId, key } resolved to text via i18n selectors. Any port of VP/BR/TT/TX/CP rules must follow that split (rules in core-contracts, messages as ErrorKey/translation selectors) — Loveable's inline strings would violate the i18n rule in CLAUDE.md.

  • Backend-first posture / mocks → tickets. pxc already annotates banking-rules.ts as interim pending RPC-150 and defers ZIP-vs-state, GLN, address verify, TIN uniqueness, ABA/sanctions/DUNS lookups to the backend. Loveable's mockServices.ts is the client stand-in for exactly those; in pxc they stay oRPC procedures, with warning inputs populated from server data. Per the "ticket every mock" rule, any new async check gets a Jira ticket + backend discussion.

  • Contract-shaped gaps to extend before porting:

    • Pagination: Loveable's 20/page numbered pager vs pxc's cursor useSuspenseInfiniteQuery + "Load more" — needs a page/offset contract param or client slicing (backend exposes nextCursor only).
    • Sort: VendorSortFieldSchema only offers name/createdAt/employeeCountEstimate — category/location/status/volume/trust-score sort + clickable headers require contract + server extension.
    • PII-reveal auditing: Loveable introduced finer pii.reveal/bank.reveal/contact.reveal/compliance.reveal permissions + reveal audit-logging; pxc gates only vendor-management:write and does not log reveals — a gap if reveal auditing is required.

  • Biggest net-new clusters for pxc (each backed by a Loveable validation/schemas/* with no pxc counterpart, and most needing new BFF fields):

    1. Business Profile & Risk / D&B validation (BR-001..027) — only compliance badges exist today.
    2. Trade Terms (TT) + Tax Identifiers (TX) rule validation — dialogs exist but validate nothing.
    3. Custom Fields / ESG / attestations (CP/GEN) — absent entirely.
    4. Cross-section (XS) + onboarding approval/SoD (OB) — absent.
    5. Request-new-vendor + duplicate/merge flow, Things-to-Fix business-validation engine + section error badges, onboarding reviewer workflow with segregation-of-duties, document reviewer approve/reject, and address-change dual approval.

  • Vendor self-scoping stays blocked. The whole vendor role + assignedVendorId + canVendorOpenPath + "My Vendor Profile" + breadcrumb-collapse + catalog ?vendor= cluster depends on the session exposing role/assignedVendorId, which pxc does not have (RPC-142 deferred to RPC-134).
