Verification Corrections (2026-06-03)#

The spec was re-verified against the actual component source and the server-side ui-platform/src/server/modules/common/df-rest-service/df-rest-service-config.js. Findings applied to mdm-api.yaml:

Endpoint names — CONFIRMED correct (resolved server-side, not in client source):

  • entityappservice/getcombined exists in df-rest-service-config.js:49-53 (timeout 360000), confirming the searchandget → getcombined mapping. (Note: the search grid actually drives the Falcor ops initiatesearch → getsearchresultdetail, which the BFF resolves to getcombined.)
  • entitymodelservice/getcomposite → /entityappmodelservice/getcomposite (df-rest-service-config.js:84-93), confirming the composite-model mapping.
  • The entityservice/* → /entityappservice/* and entitymodelservice/get → /entityappmodelservice/get key remaps are confirmed (:3-40, :59-68).

Request/response shapes — CORRECTED in spec (these were wrong):

  • attributerservice/generate: body is { targets:[{name}], support_context:[{type:"value",name,value}], contexts:{...}, getnearestPath, entityType, coalesceOptions } — there is no attributes key; support_context is snake_case; contexts is an object (not array). (rock-attribute-manage-v2.js:4057-4064)
  • nlqservice/transform response payload is at dataObjectOperationResponse.dataObjects[0].data.jsonData.query (note the .query), plus a status field. (rock-entity-search-discovery-v2.js:2841-2844)
  • modelgovernservice/validate request top-level key is entityModel (not entity); entitygovernservice/validate uses entity. Both built by createSyncValidationRequest as a {id,type,data} triple with optional onDemandTroubleshooting — no clientState. (DataRequestHelper.js:991-1004, rock-attribute-manage-v2.js:1570)
  • entityappmodelservice/getnearest (variant model): request has no query.id; filters.typesCriterion: ['entityVariantModel'], fields.attributes: ['_ALL'], contexts: [variantContextData]. (DataRequestHelper.js:2235-2257)
  • entityappservice/getcombined request is a combined-get envelope, not a bare search query. Full chain verified in ui-platform/src/server (no capture needed): client builds { params:{isCombinedQuerySearch:true}, entity:{ id/name:'combinedGet', type:'config', data:{jsonData:{searchQueries:[{serviceName, action, searchSequence, searchQuery}, ...]}} } } via createCombinedGetRequest (DataRequestHelper.js:1926, rock-entity-search-result-v2.js:4252); the server detects isCombinedQuerySearch (dataobject-route-resolver.js:222), swaps it for params.pageSize, sets isIdOnly on the highest-searchSequence leg, then DataObjectManageService.getCombined posts to /entityappservice/getcombined (DataObjectManageService.js:31-40, resolved via df-rest-service-config.js:49-53). Spec now models this as CombinedGetRequest + SearchQueryLeg, with EntitySearchRequest repurposed as the inner entityservice leg (query/fields/options/sort/authorizationType:'accommodate'). Inner-query details: options.allowLeadingWildcard (camelCase, not ALLOW_LEADING_WILDCARD) + options.to/isIdOnly; sort.attributes[] uses a dynamic attribute-name key = direction (_ASC/_DESC) with sibling sortType/contexts, plus sort.score; attributesCriterion supports exacts/operator/valueProperties; and filters uses compound and/or arrays (rock-entity-search-result-v2.js:4233-4248), not isAttributesCriterionOR. (DataRequestHelper.js:3259-3360, EntitySearchGridDataSource.js:110-129,354-364)
  • entityappmodelservice/getcomposite request: the menu-load builder uses id + fields.properties; the name-based builder uses fields.attributes. id XOR name. (rock-relationship-manage-v2.js:1304-1307, DataRequestHelper.js:74-78)

Response envelope — CORRECTED in spec (no content wrapper): The spec describes raw MDM responses, so result collections sit directly under response (response.entities, response.entityModels, response.configObjects) — NOT under response.content.*. The content wrapper seen throughout the UI is a Falcor DAL client-side artifact. Direct evidence: the pass-through getnearest handler reads res.entityModels[0] (rock-relationship-manage-v2.js:1513) and the pass-through match response reads response.entities (MatchServiceManager.js:204) — neither has content. Flattened in spec: EntityGetResponse, EntitySearchResponse, EntityModelGetResponse, CompositeModelResponse, GovernDataResponse, ConfigGetResponse (MatchSearchResponse was already correct).

Still UNVERIFIED — flagged x-unverified in spec, need a real network capture:

  • EntityMutateRequest.params.authorizationType / intent — not found in the save path (the UI sends { entities: [...] } with optional hotline / onDemandTroubleshooting).

entityservice vs entityappservice: entityappservice is an orchestration facade introduced on top of the raw entityservice persistence API. It adds app-level logic before delegating — e.g. calling matchservice/search for duplicate detection before a create. UI components always call entityappservice; entityservice is an internal downstream call made by entityappservice itself. The BFF config key is named entityservice (legacy naming) but maps to the URL /entityappservice/.... Duplicate detection therefore can occur at two layers: explicitly in the UI via MatchServiceManager → matchservice/search, and again internally within entityappservice before it delegates to entityservice.

Traced Helper Calls (previously untraced)#

Helper 1: DataRequestHelper.getBusinessConditionExternalNameByIds#

Source: ui-platform-business-components-v2/src/helpers/DataRequestHelper.js:4078
Called by: rock-entity-search-discovery-v2 (lines ~1595, ~1699) — resolves display names for business condition IDs used in workflow criteria.

Call chain:

DataObjectManager.createRequest('getbyids', req, '', { dataIndex: 'entityModel' })
  → DataObjectManager.initiateRequest()
  → FalcorManager.get() → /data/entityModelData.json (BFF Falcor)
  → BFF DataObjectManageService: entityModel → entitymodelservice/get
  → df-rest-service-config: entitymodelservice/get → POST /entityappmodelservice/get

Actual MDM endpoint: POST /entityappmodelservice/get (already in spec)

Request:

json
{
  "params": {
    "query": {
      "ids": ["<bc-id-1>", "..."],
      "filters": { "typesCriterion": ["businessCondition"] },
      "valueContexts": [{ "source": "internal", "locale": "en-US" }]
    },
    "fields": { "attributes": ["name"] }
  }
}

Response: Standard entityModels[] — extracts data.attributes.name.values[].value keyed by locale.
No new endpoint needed — businessCondition is just another typesCriterion on entityappmodelservice/get.

Helper 2: MatchServiceManager.getMatchEntityInfo#

Source: ui-platform-dataaccess/src/managers/MatchServiceManager.js:14
Called by: rock-attribute-manage-v2 before every create, and before update when identity attributes (isEntityIdentifier, isMatchAttribute, isExternalName) are modified.

Call chain:

MatchServiceManager.getMatchEntityInfo()
  → MatchServiceManager.matchServiceCall()
  → LiquidDataObjectManager.rest('/data/pass-through/matchservice/search', request)
  → BFF pass-through proxy: strips prefix → matchservice/search
  → df-rest-service-config: matchservice/search → POST /matchservice/search

Actual MDM endpoint: POST /matchservice/search (new — added to spec)

Request:

json
{
  "entity": {
    "id": "<entity-id>",
    "type": "<entity-type>",
    "data": { "attributes": { ... identity attributes only ... } }
  },
  "params": {
    "matchThreshold": 85,
    "recommendationViewEnabled": true
  }
}

Response classification logic:

  • statusDetail.probabilisticMatch: false → deterministic: any returned entity = duplicate
  • statusDetail.probabilisticMatch: true → ML-based scoring:
    • score < createThreshold → safe to create (no real duplicate)
    • score > mergeThreshold → should merge
    • between thresholds → createOrMergeList (user decides)
  • matchFound = false if result list is empty OR all scores are below createThreshold
